## Why the duration fluctuated (and the curve looked stepped)

Frames were timestamped with `performance.now()` inside the callback, but that is not the clock the engines animate on. In `rafz` (react-spring's frame loop) the physics gets a **fixed 16.667 ms on the first frame** no matter how late it arrives, and every later frame is **capped at 64 ms**. So a late first frame or a janky stretch inflated the wall‑clock duration (0.75 s → 1.5 s) while the values only advanced by the capped amount, which also produced the stair‑stepped curve: time kept moving, values didn't. Motion and GSAP suffered the same callback jitter.

## What changed

**Engine time base** (`engines/`)
- `1-spring.ts`: samples are stamped with the reconstructed physics clock (`advanceSpringClock`: 17 ms first frame, then `ceil(min(64, dt))`), which is exactly the time react-spring integrated the value to.
- `2-motion.ts`: uses `controls.time` (the timeline position the value was resolved for).
- `3-gsap.ts`: uses `tween.time()`.

**Duration decided in advance** (`model/2-duration.ts`, `state/atoms.ts`, `store/1-ui-settings.ts`)
- `estimateDurationMs` is now exact per engine: GSAP = `duration`; Motion = `calcGeneratorDuration(spring(params))` (what Motion itself precomputes); react-spring = a faithful replica of `SpringValue.advance` (1 ms semi‑implicit Euler, rest at `|v| ≤ precision/10` and `|1 − x| ≤ precision`, clamp handling).
- `getPlotDurationMs` = exact + 64 ms settle headroom for the physics engines (rest is detected mid‑frame), exact for GSAP. The axis is set from this at run start.
- The measured‑duration memory (`lastDurationBy…`, persisted `recordedDurations`) is gone, so the axis no longer depends on run history. Legacy `recordedDurations` in localStorage is dropped on load.

**Points toggle**
- New persisted `showGraphPoints` setting with a **Points** checkbox next to Auto‑update. Points are now either always shown (radius shrinks when dense instead of vanishing) or never shown.
