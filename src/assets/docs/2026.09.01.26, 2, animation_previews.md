## What I found in the reference app

I cloned `JoostKiens/react-spring-visualizer` and extracted frames from your four recordings. In `DefaultVisualizer.js`, each preview maps a single `progress` spring value through a transform, and (contrary to what the video first suggests) the **blue is the container background** (`--color-secondary`) while the **cream element is the animated one** (`--color-highlight`):

| Mode | Animated element | Mapping | Readout |

Every scene has a 3px boundary frame drawn **on top** of the content so the outline stays visible while the element overflows it.

## What I built

New files in `2-preview/` (one animation per file), all reading from the shared store:

- `1-preview-frame.tsx` — `PreviewCanvas` (square stage that fits its container via `cqw/cqh`), `PreviewFrame` (the boundary outline), `PreviewProgress`, and `usePreviewValue()`.
- `3-translate-preview.tsx`, `4-scale-preview.tsx`, `5-rotate-preview.tsx`, `6-opacity-preview.tsx` — DOM/Tailwind implementations mirroring the reference geometry above.
- `state/preview-motion.ts` — a **Valtio** proxy `{ value }` written by the engine every frame.
- `t-3-6-transform-previews.test.ts` — tests for the mappings and the store.

Changed: `2-mechanical-spring-svg.tsx` now reads the store instead of exposing an imperative `ref` handle; `8-use-engine-run.ts` writes `setPreviewValue()` / `resetPreviewValue()` and no longer needs a scene ref; `0-preview-stage.tsx` switches scenes with a plain `switch` and got `overflow-hidden` so overshoot never produces scrollbars. Deleted the monolithic `3-transform-preview-svg.tsx`.

**Why Valtio for the value and not Jotai:** the progress is a mutable scalar written imperatively from animation loops (react-spring / Motion / GSAP tickers) ~60×/s. A proxy mutation maps onto that directly and any component can subscribe with `useSnapshot` without refs or props, which is what makes the scenes drop-in reusable. Discrete UI choices (engine, params, selected scene) stay in the existing Jotai atoms.
