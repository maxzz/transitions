I'll check how each engine records frames and whether any of them can be sampled ahead of real time.

Yes. You can sample each engine’s solver in a tight loop and have the full curve before the first preview frame. You do not need to run the animation faster than real time.

The live engines are all rAF-driven today (`SpringValue.start`, Motion `animate`, `gsap.to`), which is why the first plot only appears as frames arrive. The solvers underneath are deterministic, and you already use that for the time axis in `getPlotDurationMs` / `estimateDurationMs`.

**What “pre-record” should mean here**

Keep the preview at normal speed. Separately, before `runStatus` becomes `"running"` (or in the same turn, synchronously), walk the solver and write `SamplePoint[]` into `runResultAtom`. The plot and playhead then treat the first playback like a replay: settled samples exist, so `showGraphPlayheadAtom` is already true.

Speeding up the real tween (`timeScale`, a huge `speed`) is a poor fit. It still waits on rAF, skips frames, and can miss rest detection.

**Per engine**

| Engine | Offline sample | Match to live preview |
| --- | --- | --- |
| **GSAP** | `gsap.parseEase(formatGsapEase(params))`, then `value = ease(t / duration)` at a fixed step | Exact. Duration and ease are closed-form. |
| **Motion** | The same `spring({ keyframes: [0, 1], ...params })` generator you already pass to `calcGeneratorDuration` — call `next()` until `done` | Exact. Motion resolves the spring analytically. |
| **React Spring** | The Euler loop already in `reactSpringDurationMs` — emit `{ elapsedMs: stepsDone, value: position }` instead of only returning the rest time | Very close. That loop is a replica of `SpringValue.advance` (1 ms steps, same rest test). Live recording still uses rafz’s 16.7 / 64 ms caps, so native rAF samples will be sparser and slightly jittered. |

A 1 ms step over your 30 s cap is tens of thousands of iterations — typically well under a millisecond. No worker needed.

**Tradeoff with the current graph**

The README and `useEngineRun` treat the curve as **native frame samples**, not an analytic path. Offline sampling is denser and frame-timing-independent. For a playhead that is what you want (same idea as the Motion AI Kit video). After the live run finishes you can either:

- keep the precomputed curve (simplest; playhead stays on that path), or
- replace it once with decimated live samples (current “what the engine actually painted” story).

If the playhead interpolates the precomputed path while the preview is the live engine, GSAP and Motion will line up. React Spring may be a fraction of a frame off because of rafz. That is usually invisible.

**How it would slot in**

1. Add something like `sampleEngine(engineId, params, stepMs) → SamplePoint[]` next to `estimateDurationMs`.
2. In `startRun`, if there is no kept result, build those samples and set `runResultAtom` immediately (same `plotDurationMs` you already compute).
3. Leave `showGraphPlayheadAtom` as it is: recording **and** settled samples. The first run then shows the playhead because samples exist from the start.
4. Still start the real engine for the preview; do not drive the preview from the sampled array unless you want to drop native playback.

So: yes, and it is the right way to get a playhead on the first play. Offline solver sampling, not a sped-up recording. I can implement that in Agent mode if you want.
